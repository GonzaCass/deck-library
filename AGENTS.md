# Public project communication

Write release notes for someone who has never read a development conversation.
Lead with the problem fixed or the behavior added. Include relevant upgrade steps
and limitations. Avoid conversation references, personal machine details, private
paths, user-specific instructions and offers to continue working.

Release notes do not report test suites, test counts, test environments or
"not tested" disclaimers. Mention a check only when a person did it on a Steam
Deck or in a game, in one plain sentence, and state real limitations as limitations.
Scan the English text with unslop's banned_phrase_scan.py before publishing.
User-reported FPS are approximate observations, not benchmarks or guarantees.
A published community preset is not a verified game.

Never include credentials, personal library data or original game files in commits,
release notes, diagnostics or release archives. Preserve historical release facts
when revising their wording. Product UI text should be short, concrete and correctly
spelled; keep Spanish and English translations complete.
